# Next-Gen Parking Lot - Machine Coding Solution

A complete, object-oriented Java solution for the **Next Generation Parking Lot** machine coding problem.

## Problem Overview

Design a command-line parking lot system with:
- Multiple floors
- Multiple vehicle types (Car, Bike, Truck)
- Type-specific parking slots (1st slot = Truck, next 2 = Bike, rest = Car)
- Ticket-based parking/unparking
- Display queries (free count, free slots, occupied slots)

## How to Run

```bash
cd parking-lot/src/main/java
javac com/parkinglot/Main.java
java com.parkinglot.Main < sample_input.txt
```

## Design Decisions

### 1. Models
- **VehicleType** - Enum keeps it type-safe and extensible.
- **Vehicle** - Simple POJO; could be subclassed for future vehicle-specific behavior.
- **ParkingSlot** - Knows its slot number, allowed vehicle type, and currently parked vehicle.
- **ParkingFloor** - Initializes slots with the required pattern (Truck, Bike, Bike, Car...).
- **ParkingLot** - Top-level aggregate containing floors.
- **Ticket** - Immutable result of parking operation.

### 2. Service Layer
- **ParkingLotService** - Pure business logic with zero I/O.
- **Strategy for slot finding:** Iterates floors 1→N, then slots 1→N, matching both vehicle type and availability. This naturally satisfies "lowest floor, lowest slot number."
- **Ticket parsing:** `unparkVehicle` parses the ticket ID, validates parking lot/floor/slot, and checks occupancy.

### 3. Command Layer
- **CommandHandler** - Handles all 5 commands (`create_parking_lot`, `park_vehicle`, `unpark_vehicle`, `display`, `exit`).
- Delegates to service and prints exact required output format.

### 4. Extensibility (Optional Requirements)

| Extension | How the code supports it |
|-----------|------------------------|
| New Vehicle/Slot Types | Add to `VehicleType` enum; slot initialization logic in `ParkingFloor` can be refactored into a `SlotAllocationStrategy` |
| Different Slot Finding Strategy | Extract `findFirstAvailableSlot()` into an interface (e.g., `NearestSlotStrategy`, `CheapestSlotStrategy`) |
| New Commands | Add new case in `CommandHandler.handle()` without touching service logic |
| Multiple Parking Lots | Change `ParkingLotService` to hold a `Map<String, ParkingLot>` instead of a single reference |
| Thread Safety | Synchronize `parkVehicle`/`unparkVehicle` or use `ConcurrentHashMap` for slot tracking |

## Key Implementation Details

### Slot Initialization (per floor)
```
Slot 1     → TRUCK
Slot 2, 3  → BIKE
Slot 4..N  → CAR
```

### Ticket ID Format
```
<parking_lot_id>_<floor_no>_<slot_no>
Example: PR1234_2_5
```

### Display Output
- `free_count` → `No. of free slots for <TYPE> on Floor <F>: <COUNT>`
- `free_slots` → `Free slots for <TYPE> on Floor <F>: <comma-separated-slot-nos>`
- `occupied_slots` → `Occupied slots for <TYPE> on Floor <F>: <comma-separated-slot-nos>`

## What Interviewers Look For

1. **Clean OOP** - Separate models, service, and command layers.
2. **Correctness** - Output must match the expected format precisely.
3. **Edge Cases** - Full lot, invalid ticket, duplicate unpark, empty displays.
4. **Extensibility** - Easy to plug in new strategies, commands, or vehicle types.
5. **Readability** - Small methods, meaningful names, consistent style.

## Time Complexity

- **parkVehicle:** O(F × S) where F = floors, S = slots per floor (worst case scans all slots)
- **unparkVehicle:** O(F + S) to find floor and slot
- **display:** O(F × S) per query

These are optimal for the given constraints in a typical machine coding round.
